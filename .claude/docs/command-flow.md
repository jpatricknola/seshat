# Command Flow

End-to-end path from user input to Ableton state change, for both modes.

## MCP mode (primary)

```
Claude Desktop / Claude Code
        │  MCP tool call: set_track_pan {"track": 0, "value": -1.0}
        │  (stdio via `mix mcp`, or streamable HTTP with the app running)
        ▼
Seshat.MCP.Server                       ← components generated by Seshat.MCP.Tools
  → Peri validates params against the generated schema
  → returns ATOM-keyed params
        ▼
Seshat.Tools.Handlers.call/2            ← normalises keys to strings
        ▼
   (see "Shared tail" below)
```

No system prompt of ours is involved. The client's model reasons using only the
tool names, descriptions, and schemas from `Seshat.Tools.Definitions`.

## API-key mode (dev / fallback)

```
Browser → SeshatWeb.AssistantLive
  handle_event("submit", ...)
  → start_async(...)
        ▼
Seshat.Agent.run/2
  → POST api.anthropic.com/v1/messages with:
      - @system_prompt (index bases, note names, beat math, chord intervals)
      - Definitions.to_anthropic_tools()
      - conversation history
  → loops on stop_reason == "tool_use", max 10 iterations
  → executes each tool_use block, feeds tool_result back
        ▼
Seshat.Tools.Handlers.call/2            ← string-keyed params from the API
        ▼
   (see "Shared tail" below)
```

Model: `claude-haiku-4-5-20251001`, max_tokens 1024.

## Shared tail

```
Seshat.Tools.Handlers
  → call/2 validates params against the tool's schema
    (Seshat.Tools.Validation — declared types, bounds, enums, required;
     rejects before anything is sent, in BOTH modes)
  → do_call/2 clause per tool name
  → simple tools call Transport directly
  → multi-step tools build a %Command{} and hand it to Registry
        ▼
Seshat.Commands.Registry.execute/1
  → pattern matches on command type
  → sequences multi-step operations
     (create_track = query num_tracks → create → set name)
     (write_notes  = ensure clip exists → add notes)
        ▼
Seshat.OSC.Transport (GenServer)
  → encodes via Seshat.OSC.Message
  → send_message/2 is fire-and-forget UDP to port 11000
  → query/3 sends and awaits a reply on 11001 (5s default timeout;
    callers pass 15s for browsing, 30s for device loading)
  → broadcasts all inbound messages on the "osc:in" PubSub topic
        ▼
AbletonOSC (Python MIDI Remote Script) → Ableton Live
        │
        ▼
Seshat.Session.State (subscribed to "osc:in")
  → updates the in-memory mirror as Ableton pushes changes
  → refresh/0 re-queries after structural changes (track create/delete)
```

## Why the split

`Handlers` is the seam. Everything above it differs per mode; everything below
is shared. When adding a tool you touch `Definitions` and `Handlers` — never
the mode-specific layers. See [adding-a-tool.md](adding-a-tool.md).

## Failure modes to know

- **Wrong OSC address** — silent. UDP, no reply, no error. Always check
  [docs/abletonosc-api-docs.md](../../docs/abletonosc-api-docs.md).
- **Ableton not running** — `Transport.query/3` blocks then exits at the
  timeout. `send_message/2` returns `:ok` regardless; it can't know.
- **Port 11001 in use** — Transport falls back to an ephemeral port and logs a
  warning, which means replies never arrive. Queries then time out while sends
  appear fine.
- **Atom vs string keys** — handled in `Handlers.call/2`. Before that fix, every
  MCP tool call fell through to `{:error, "Unknown tool: ..."}`.
- **Two layers reject bad params, and they say different things.** In MCP mode
  Peri refuses first, at the wire, as a JSON-RPC error — clients may surface
  that as a bare "Invalid params", and its nested-array message is empty.
  `Validation` is the authoritative check (it also catches what Peri's bounded
  clauses miss, such as `1.5` for an integer) and produces the model-facing
  text, but in MCP mode it is only reached for what Peri lets through. Roadmap:
  "Model-readable rejections for invalid tool parameters in MCP mode".
