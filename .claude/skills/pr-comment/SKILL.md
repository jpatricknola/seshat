Review this change and leave the findings as a comment: **$ARGUMENTS** (no
argument → the PR for the current branch).

Use [pr-review](../pr-review/SKILL.md) as the canonical review procedure. Read
it completely and follow its review criteria, verification steps, severity
ordering, and output format. This skill changes only the delivery and mutation
rules below; when they conflict with `pr-review`, these rules win.

1. **Resolve a PR.** The argument must identify a PR, or a remote branch with
   an open PR. With no argument, use the current branch's PR. If no PR exists,
   stop and report that instead of reviewing a guessed change set or opening a
   PR.

2. **Verify only the revision under review.** `pr-review`'s `mix compile`,
   `mix test` and `mix format --check-formatted` steps run against the working
   tree, and rule 3 forbids making the tree match — so those commands are
   evidence about the PR only when the tree already *is* the PR. Before running
   any of them, compare `git rev-parse HEAD` against the PR's `headRefOid` and
   check that `git status` is clean. Run them only when the SHAs match and the
   tree is clean; otherwise skip all three, review the target revision read-only
   (`git diff`, `git show`, `gh pr diff`), and say verification was skipped and
   why. A comment claiming a PR compiles and passes when the tree held different
   code is worse than one that admits it checked nothing — it is the one part of
   a review a reader cannot re-derive from the diff.

3. **Do not modify repository files.** This is read-only review work: do not
   fix code, format files, restore files, switch branches, stash changes, or run
   any command known to rewrite tracked files. Record the initial repository
   status and leave every existing tracked and untracked file exactly as found.
   Turn every proposed change into a finding or recommendation in the comment.

4. **Read the existing discussion.** Include the PR's comments and reviews
   when gathering its metadata. Do not repeat a finding that was already made
   and resolved or answered. Report a previously raised but still-unfixed
   finding as still open.

5. **Post the review as a PR comment.** Preserve `pr-review`'s verdict-first
   review format and add one line saying what verification ran or why it was
   skipped. Write as the repository owner: plain prose, no attribution footer,
   no "generated by" line, and no emoji headers.

   Pass the comment body to `gh pr comment <pr> --body-file -` through stdin.
   Do not create a scratch file or interpolate the long comment into a shell
   command. Posting this comment is the only external mutation this skill
   authorizes.

6. **Report completion.** Return the comment URL from `gh` and the verdict in
   one or two lines. Do not reproduce the posted comment.
